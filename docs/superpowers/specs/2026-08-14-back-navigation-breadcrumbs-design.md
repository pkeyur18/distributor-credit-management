# Back-navigation breadcrumbs — Structure / Member Detail / Volume Entry

**Ref:** `documents/design/ui-prototype-v2.html` (client-approved), §breadcrumb (lines 147-153, 1309-1317), §Structure view (1907-1980), §Member Detail breadcrumb (1825), §Volume Entry breadcrumb (2391)
**Branch:** `feature/back-navigation-breadcrumbs` off `develop`

Pure UX addition — no business rule, calculation, or data-model change. The
prototype ships a working, client-approved breadcrumb/back-link system on
these three screens that the current React build never carried over; this
spec ports it faithfully rather than reinventing it.

## 1. What the prototype actually does (not assumed, verified against source)

The prototype's back link is not a fixed per-screen string. `APP.navStack`
is a generic push/pop stack of `{view, params}`; every `P.nav(...)` call
(sidebar click, table row, search result, "View in structure" button, "Record
volume" button) pushes the screen being left. `backTargetLabel()` reads the
top of that stack **at render time** and resolves a human label: a member
route resolves to that member's name, a structure route resolves to
`"Structure (<name>)"`, everything else falls back to a static
`ROUTE_LABELS` map. `backLink()` renders `"← Back to " + backTargetLabel()`,
present only when the stack is non-empty.

Structure's breadcrumb additionally renders `ancestorTrail(currentId)` —
root-first, inclusive of the current member — each ancestor a link that
re-roots the view (`nav('structure', {id}, {replace:true})`, which does not
push the stack, so re-rooting never disturbs where "back" points). The
member's own name is the trail's last, non-clickable entry.

Member Detail's breadcrumb is `backLink() / Home / <member name>` — `Home`
is a fixed link, always present, always to `/`.

Volume Entry's breadcrumb is just `backLink()` — nothing else.

Breadcrumb renders above the page title, inside the sticky header
(`shell()`: banner → breadcrumb → title/actions).

## 2. Backend — `get_ancestor_chain`

New command, `m4_search` module (alongside `get_direct_children_chart`,
`get_member_detail` — the other read/display queries).

```
get_ancestor_chain(member_id: i64) -> { chain: Vec<AncestorNode> }
AncestorNode { id: i64, name: String, isActive: bool }
```

Implementation mirrors `m3_calc::chain_to_root`'s existing upward-walk idiom
(`while let Some(parent) = introducer_of(...)`) — a loop of indexed
primary-key point lookups, not a recursive CTE (the codebase reserves CTEs
for the downward subtree walk in `get_direct_children_chart`). Collect ids
leaf-to-root, batch-fetch `name`/`is_active` in one `SELECT ... WHERE id IN
(...)`, return root-first with the requested member last.

Wiring follows the existing per-command pattern exactly: domain fn in
`m4_search/mod.rs` → thin `#[tauri::command]` wrapper in `commands.rs`
(`require_session`, `locked_conn`, delegate) → name added to
`ALL_COMMAND_NAMES` in `command_names.rs` → registered in
`invoke_handler(tauri::generate_handler![...])` in `lib.rs` → `"allow-get-
ancestor-chain"` added to `capabilities/default.json`. The
`permissions/autogenerated/*.toml` file is build-generated (`build.rs` /
`tauri_build`), nothing hand-written there.

Member-not-found → `AppError::NotFound`, same as every other id-keyed
lookup in this module.

**Performance:** cost scales with chain *depth*, not member count — each hop
is an indexed PK lookup, in-process SQLite, no network round trip. Rule-32
warns-but-allows past the configured max depth (no hard cap), so worst case
is a pathologically deep single chain; even 25k sequential indexed PK
lookups in one connection is low-single-digit milliseconds. Realistic trees
per TR-7 are wide/shallow. One IPC call per Structure screen load
(triggered on `currentId` change), unrelated to the existing large-tree
render path (`get_direct_children_chart`, the "one branch open at a time" /
Full Hierarchy gate) which this work does not touch.

## 3. Frontend — navigation-history mechanism

New `src/lib/navigation-history.tsx`: a `NavigationHistoryProvider` mounted
once in `app-shell.tsx` around `<Outlet/>`, using `useLocation()` +
`useNavigationType()`.

- **PUSH**: push `{path, label}` for the screen being left onto an
  in-memory stack (React state, not ref, so consumers re-render).
  `label` comes from whatever that screen last reported via
  `useRouteLabel`, falling back to a static `ROUTE_LABELS`-equivalent map
  keyed by path for screens that never call it (Reports, Settings, Audit,
  Monthly Close).
- **REPLACE**: no-op — matches the prototype's `{replace:true}` re-root,
  which never touches `navStack`.
- **POP** (back button / our own `go()` below): pop one level.

Two hooks:
- `useRouteLabel(label: string | undefined)` — screens call this with
  their current display identity (`member.name`, `"Structure
  (${rootNode.name})"`, `"Volume entry"`); `undefined` (still loading)
  leaves the previous value in place.
- `useBackTarget()` — returns `{ show, label, go }` for the *current*
  screen: `show` is false with an empty stack (fresh load / deep link),
  `go = () => navigate(-1)`.

Cost: a stack of plain strings, bounded by screens actually visited this
session. No relation to hierarchy size.

## 4. Screen changes

**`components/breadcrumb.tsx`** (new) — presentational only: optional back
link (`ChevronLeft` + label, `lucide-react`, already used elsewhere in this
codebase for directional affordances), then `/`-separated crumbs, current
crumb bold/non-interactive. Added as an optional `breadcrumb` prop on
`PageHeader`, rendered above the title row (matches prototype's
banner → breadcrumb → title ordering).

- **`structure.tsx`**: fetch `get_ancestor_chain` on `currentId` change
  (parallel to the existing children-chart fetch, independent effect).
  Render `useBackTarget()` + the trail; each non-current ancestor navigates
  `/structure/${id}` with `{ replace: true }`. Calls
  `useRouteLabel(rootNode && \`Structure (${rootNode.name})\`)`.
- **`member-detail.tsx`**: render `useBackTarget()` + fixed `Home` link
  (`navigate("/")`) + current member name. Calls
  `useRouteLabel(detail && member.name)`.
- **`business-volume-entry.tsx`**: render `useBackTarget()` only. Calls
  `useRouteLabel("Volume entry")`.

No other screen's rendered output changes. Existing `navigate(...)` call
sites across the app (sidebar `NavLink`s, tree-node view-detail buttons,
table rows, search results, "View in structure" / "Record volume" buttons)
need no per-call-site edits — the provider observes route transitions
generically, it does not require each call site to opt in.
